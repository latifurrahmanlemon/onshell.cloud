## 1. Plan & billing redesign + self-serve upgrade

**The bug:** `growth.tsx` styled its panels with `.panel-title` / `.panel-hint`,
which were defined in no stylesheet. `.panel` only draws the frame, so the billing
panels had **zero padding** and no gap between them — that was the missing margin.
There was also no upgrade path: the only button linked to `/#pricing`.

**API** — `routes/modules/growth.ts`
- `GET /me/growth` also returns `plans[]` (every active plan with limits, prices,
  features) and `canManageBilling`. Current plan and suggested upgrade share one
  `toConsolePlan()` shape.
- New `POST /me/billing/checkout` — owner/admin only, 10/min. Rejects the free
  plan and the plan the workspace is already on.
- With no payment provider configured there is no hosted page to open, so the
  request is filed as a `ContactMessage` (topic `sales`) and returns
  `selfServe: false` with a message. Keeps the button honest on invoice-by-hand
  deployments instead of dead-ending at the placeholder `/checkout/mock` URL.

**Web** — `growth.tsx`, `console.css`, `api.ts`
- Four stacked panels in a `.gr-stack`, each padding its own content.
- Plan grid with a monthly/yearly toggle, per-plan yearly saving %, and a CTA
  resolved per plan: current / upgrade / "talk to us about switching" (downgrades
  go through a human) / "owner only".
- Mobile pass at ≤720px: one card per row, stacked headers, full-width controls.

**Verified in browser:** panels padded and spaced; usage meters go red at limit;
yearly toggle switches to $190/$490 and shows "Save 17% versus monthly"; clicking
"Start 14-day trial" shows the sales-followup notice; the request landed in
`ContactMessage` and `AuditLog` (`billing.checkout.started`). At 500px: cards
stack one per row with full-width CTAs.

## 2. AI assistant as a floating chat widget

**API** — `routes/modules/public.ts`: new `POST /public/ai/chat`, 12 per 5 min per
IP. Stateless by necessity — an anonymous visitor has no `AiThread` to write to —
so the client replays recent turns. Guest replies capped at 700 output tokens,
with a prompt suffix forbidding any implication it can act inside a workspace.

**Web** — new `components/ai-chat-widget.tsx` + `ai-chat.css`, mounted once in
`app/layout.tsx`, so the bubble is on marketing pages, login, signup, console and
admin alike. Renders nothing until an admin enables the assistant. Two modes
behind one UI: signed in → `/ai/messages` with persisted threads; anonymous →
`/public/ai/chat` with the transcript in `sessionStorage`.

`z-index: 39` — below `.drawer-overlay` (40) so modals cover it, and below the
fullscreen terminal (60). `.console-toast` moves up to `bottom: 82px` so the toast
and the bubble stop overlapping.

Sidebar entry "AI Assistant" removed; `console/assistant.tsx` deleted along with
~490 lines of dead `.ai-*` CSS.

Also added `?view=` deep linking to the console (in an effect after mount, not
initial state, to avoid a hydration mismatch). This fixes the pre-existing
`/console?view=settings` link in the public profile menu, which did nothing.

**Verified in browser:** bubble absent while the assistant is disabled, present
once enabled; guest starters on the public site, member starters and "Saved to
your workspace" when signed in; on a bad upstream key the error renders and the
question is restored to the composer for retry. One defect found and fixed: on
≤560px the close bubble sat on top of the composer's send button — the bubble is
now hidden while the sheet is open, since the sheet has its own close control.

## 3. Selective host export

The route is `GET /hosts/export` in `routes/modules/host-transfer.ts` (not
`hosts.ts`).

- `ids` query param: comma-separated, deduped, max 400.
- `id: { in: ids }` is spread *after* `...accessFilter`, so it can only narrow —
  unauthorised or stale ids fall out of the result set rather than 404.
- Over the cap it **rejects** rather than truncating; exporting 400 of 600
  selected hosts would look like a complete export.
- The cap is set by the URL, not the database: the export is a direct browser
  navigation, so ids ride in the query string. Measured, ~550 cuids is where
  Fastify starts returning 431, so 400 keeps the clear message reachable.
- Hosts table: per-row checkboxes, select-all with indeterminate state that only
  touches filtered rows, "N selected" + Clear, and "Export N selected" vs
  "Export all".

**Verified in browser:** ticking two rows flips the label to "Export 2 selected",
the header checkbox goes indeterminate, and the export URL carries exactly those
two ids. Over HTTP: `ids` narrows the CSV to the selection, unknown ids are
ignored, 401 unique ids returns "Select at most 400 hosts per export."

## 4. Credential-free local terminal and files

Every workspace gets a built-in host, "This computer", that opens a shell and
browses files on the machine the gateway runs on with no credential. This is what
was throwing *"This host has no credential attached"*.

**Schema** — `Host.isLocal`, migration `20260728120000_add_local_hosts`.

**API**
- `provisioning.ts`: `ensureLocalHost()` — idempotent, records `127.0.0.1:22` for
  display only (no socket is ever opened). No-op when `LOCAL_SHELL_ENABLED=false`.
- Called on both signup paths, and lazily from `GET /hosts` so existing
  workspaces are backfilled without a data migration.
- `sessions.ts`: local hosts skip credential lookup and send `transport: "local"`.
  RDP is refused, and `localShellEnabled` is re-checked here so flipping the flag
  off also disables rows that already exist.
- `hosts.ts`: PATCH and DELETE refuse the local host (`local_host_immutable`).

**Gateway** — new `protocols/local.ts`
- `transport: "local"` on `POST /sessions`; the `/ws/ssh/:id` and sftp-list
  handlers both branch on it.
- Real pty via `node-pty` (an **optionalDependency**, imported through a variable
  specifier so a host where the native build failed still compiles and boots).
  Falls back to a piped `$SHELL -i` — commands work, job control and resize do
  not — and logs why.
- `scripts/fix-node-pty-permissions.mjs`, wired to root `postinstall`: Yarn's
  extraction drops file modes, so node-pty's `spawn-helper` lands 0644 and every
  pty spawn fails with a bare `posix_spawnp failed.`. That is exactly what
  happened here — without the chmod the terminal silently ran degraded.

**Web:** hosts table shows a "Built-in" pill, "No credential needed" instead of
address:port, and no Edit/Delete. The file browser trusts the path the gateway
resolved, so the breadcrumb shows where `.` actually landed.

**Verified in browser:** a live zsh prompt on "This computer" with no credential;
`echo "…$(uname -s) $(sw_vers -productVersion)"` returned `Darwin 26.5.2`; the
file browser opened at `/Users/latifur` and navigated into `.claude`. Over HTTP:
PATCH/DELETE/RDP on the built-in host all refused with the intended errors.

## 5. SFTP listing moved behind the API

Found while finishing #4, and a consequence of it. The browser called the
gateway's `/sessions/:id/sftp/list` **directly**, and `GATEWAY_SHARED_SECRET` is
set nowhere in the deploy config — so `gateway.onshell.cloud` answered that route
to anyone holding a session id. Pre-existing, but #4 escalated it from "lists a
customer's remote server" to "lists the Onshell server's own filesystem".

- New `GET /sessions/:sessionId/files?path=` on the API: authenticated, scoped by
  organization and per-host grants, keyed by the **Onshell** session id so the
  gateway's internal id is no longer exposed to the client at all.
- `consoleApi.listFiles()` replaces the direct `fetch` to `gatewayBaseUrl`; the
  console no longer touches the gateway over REST at all, only the WebSocket.
- `GATEWAY_SHARED_SECRET` and `LOCAL_SHELL_ENABLED` documented in `.env.example`
  and threaded through `ecosystem.config.cjs` (empty by default — a hardcoded
  fallback would be identical on every deployment, i.e. no secret at all).

**Verified:** with the secret set, unauthenticated `GET /sessions` on the gateway
returns 401 while the same call with the bearer returns 200; the console still
opened a session, listed a directory, and ran a terminal throughout. Without a
session cookie the new API route returns 401.

## 6. Turnstile lockout — `captcha_required` with no captcha on screen

Reported symptom: after switching bot protection on from `/admin`, **no one could
log in anywhere and no captcha was shown**. Reproduced locally. Two independent
bugs, each of which produces exactly that, and neither leaves a way back in
because the admin panel is behind the login form it broke.

**Bug 1 — client and server disagreed about whether a challenge was required.**
`verifyTurnstile` enforced on the raw `enabled` column, while
`getPublicTurnstileConfig` only told the browser to render a widget when
`enabled && siteKey && encryptedSecretKey`. A row with `enabled = true` and no
site key therefore demanded a token for a widget that could not be rendered — a
permanent lockout. Both now read one predicate, `isTurnstileUsable()`, and an
enabled-but-incomplete row is logged as an error and **not** enforced: refusing
every visitor over an unrenderable widget is an outage, not bot protection.
Covered by `apps/api/src/lib/turnstile.test.ts` (5 cases).

**Bug 2 — `/public/site-config` was cacheable and failed silently.** It sent no
`cache-control` at all, so a CDN or the browser's heuristic cache could serve a
snapshot taken *before* Turnstile was enabled; and on any non-2xx or network error
the client cached a `FALLBACK` that says "no challenge configured". Either way the
browser renders no widget while the API requires a token, and the user gets an
opaque `captcha_required` forever. Now:
- the endpoint sends `cache-control: no-store`, and the client fetches with
  `cache: "no-store"`;
- a failed load is no longer cached, so a retry is possible;
- `useTurnstile().recoverFromServerRejection(errorCode)` — wired into login and
  signup — drops the cached config and remounts the widget when the server
  rejects for a challenge the page never displayed. The first attempt fails with
  "Bot protection needs to load before you can sign in", the widget appears, and
  the retry succeeds.

**Recovery hatch:** `TURNSTILE_DISABLED=true` (documented in `.env.example`,
threaded through `ecosystem.config.cjs`) makes the API ignore Turnstile entirely
so a locked-out operator can sign in and fix the settings without touching the
database. Deliberately env-only — it must not be reachable from the UI it guards.

**Verified:** with `enabled=1, siteKey=NULL`, login returns 200 and the server
logs "Turnstile is enabled but incomplete … not enforcing" (before the fix: 400
`captcha_required`). With a tab loaded *before* Turnstile was switched on, the
first submit shows the recovery message and the widget appears, and the second
submit logs in. With `TURNSTILE_DISABLED=true` and Turnstile still enabled in the
database, login returns 200 and the public config reports `enabled: false`.

## One thing worth deciding

`LOCAL_SHELL_ENABLED` defaults to **on**, as asked, so a new workspace gets a
working terminal immediately. Be deliberate about that on a shared multi-tenant
deployment: it hands every account that signs up a shell on the gateway box, all
of them the same box, with the gateway process's privileges. The flag exists so it
can be turned off without touching code; the sensible split is on for self-hosted
and single-tenant, off for shared SaaS.

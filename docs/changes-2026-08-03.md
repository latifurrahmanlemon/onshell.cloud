## 1. The failed migration — a table name in the wrong case

`20260731174638_add_agent_devices` opened with

```sql
ALTER TABLE `host` ADD COLUMN `isAgent` ...
```

but the table is `Host`. Every other migration in the repo spells it `Host`; Prisma
emitted the lowercase form for these last two only.

MySQL decides whether that matters with `lower_case_table_names`:

| | value | effect |
| --- | --- | --- |
| macOS (the laptop this was generated on) | **2** | names compared case-**in**sensitively — `host` finds `Host` |
| Linux (the server) | **0** | case-sensitive — `host` is a different table, and it does not exist |

So the migration passed locally and failed on the server with `Table 'onshell.host'
doesn't exist`. Prisma left it `finished_at = NULL`, and from then on refused to apply
it *or* `20260731180535_agent_enroller_nullable` — which had the same defect in three
more statements (`agentdevice`, `agentpairingcode`).

Both files now use the created casing. Nothing else about them changed: no columns, no
constraints, no ordering.

Applied to the dev database and checked for drift —
`prisma migrate diff --from-schema-datasource --to-schema-datamodel` reports **no
difference**, so the migration history now reproduces `schema.prisma` exactly.

### Recovering the server

Written up in [deploy-cloudpanel.md §16.1](deploy-cloudpanel.md) so it is where somebody
will look next time. The short version:

```bash
# 1. read the real error, and confirm how much of the migration landed
mysql -u onshell -p onshell -e "SELECT migration_name, finished_at, logs
  FROM _prisma_migrations ORDER BY started_at DESC LIMIT 3\G"
mysql -u onshell -p onshell -e "SHOW TABLES LIKE 'Agent%';
  SHOW COLUMNS FROM \`Host\` LIKE 'isAgent';"

# 2. with the fix pulled, mark the attempt as not-applied and re-run
yarn workspace @onshell/api prisma migrate resolve \
  --rolled-back 20260731174638_add_agent_devices
yarn db:deploy && yarn db:status
```

Step 1 is not optional. MySQL DDL is not transactional, so a migration can stop halfway;
`--rolled-back` only edits Prisma's bookkeeping and undoes **nothing** in the database.
Here the bad statement is the first one in the file, so the expected result is that no
`Agent*` table and no `Host.isAgent` exist and there is nothing to clean up — but that
should be seen rather than assumed. If any of it did land, drop it by hand first or the
retry fails on `Duplicate column name`.

Do not reach for `--applied`. That tells Prisma the work is done, and the columns then
never get created at all.

## 2. Why nothing caught it — CI has never run

`.github/workflows/ci.yml` triggers on `main`. The repository's default branch is
`master`, and there is no `main`. **The workflow has therefore never executed once.**

That is the actual defect here. The job already does the exact thing that would have
caught this: it runs `yarn db:deploy` against `mysql:8.4` on `ubuntu-latest`, which is
case-sensitive. It would have failed on the commit that introduced the migration.

- Trigger corrected to `master`, with a comment saying why it matters.
- New `yarn check:migrations` (`scripts/check-migration-case.mjs`) runs first. It builds
  the set of real table names from `schema.prisma` (honouring `@@map`) plus every
  `CREATE TABLE` in the migration history — relation tables and since-dropped tables
  never appear in the schema — then flags any table identifier that matches one of them
  case-insensitively but not exactly. Unknown names are left alone, so it does not
  invent failures for tables it cannot account for.

  Verified both ways: it passes on the corrected tree (11 migrations, 41 tables), and
  restoring the lowercase `host` makes it exit 1 pointing at the file and line.

The script exists as well as the CI database step because it names the problem in one
line, where a `db:deploy` failure means reading a Prisma error and knowing this platform
difference exists.

## 6. Deploy runbook was missing three environment variables

`GATEWAY_SHARED_SECRET`, `LOCAL_SHELL_ENABLED` and `TURNSTILE_DISABLED` are in
`.env.example` and threaded through `ecosystem.config.cjs`, but not in the `.env` block
of [deploy-cloudpanel.md](deploy-cloudpanel.md) — the file somebody actually copies from.
That is the likely reason `GATEWAY_SHARED_SECRET` is still unset in production, which is
July's still-to-do item 3.

All three are now in that block with the consequence of getting them wrong stated
inline: an empty shared secret leaves the gateway's REST routes unauthenticated to anyone
holding a session id; `LOCAL_SHELL_ENABLED=true` on a shared deployment hands every
account a shell on the VPS. `openssl rand -hex 32` added to the secret-generation snippet.
